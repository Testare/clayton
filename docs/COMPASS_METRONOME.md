# Compass — Metronome

**Module:** `claytonlib/metronome_compass/`  ·  **Entry point:** `metronome_compass(inputs)`

This is the **calibration** tool and the current focus of the project. The Safari
Zone itself doesn't expose much randomness, so before an attempt we calibrate our
timers somewhere that does. The setup: fight Magikarp (a fixed, tiny movepool)
against a Metronome user (a max-bulk, min-offense Lv 7 Chansey) in Blackthorn's
water. Metronome fires a random move each turn, so the exact sequence of moves and
their outcomes is a high-entropy fingerprint of the battle seed — enough to pin
down which seed we hit, and by extension how the real (variable) frame rate is
behaving over time.

> This tool underpins the frame-rate investigation described in
> [APPROXIMATE_STATE_OF_THE_PROJECT.md](APPROXIMATE_STATE_OF_THE_PROJECT.md) and is
> exercised in the `Metronome Compass Testing.ipynb` notebook.

## Inputs

```python
@dataclass
class CompassMetronomeInput:
    opponent:       MetronomeOpponent   # the Metronome user (e.g. Chansey)
    key_seed:       int
    target_delay:   int
    initial_time:   dt.datetime
    window:         int                 # ± delays searched around target_delay
    magikarp_level: int                 # < 15 ⇒ Splash only; ≥ 15 ⇒ Splash + Tackle
    known_moves:    tuple[int, ...] = ()  # move numbers Metronome is known (not) to pick
    second_window:  int = 0             # widen the seconds window to absorb frame-rate drift
```

`MagikarpGender` (male/female) is also asked interactively, because Attract —
which Metronome can select — only lands on the opposite gender.

## How candidate generation works

`_generate_candidates` enumerates a uniform *seconds × delays* grid: a single
center second (derived from the target delay's offset) is paired with every delay
in the `±window` range, producing the two canonical seeds per delay plus any extra
seconds from `second_window`. This is deliberately a **superset** of the strictly
reachable seeds so that imprecision in the ~59.8261 Hz frame rate doesn't
accidentally filter out the true seed (the "wider compass windows" mitigation).

## Turn simulation

For each candidate seed, `precompute_path(seed, magikarp_level, opposite_gender,
known_moves)` simulates the full battle forward. `simulate_turn(...)` models a
complete turn in two halves — the Metronome move and the Magikarp move — including
accuracy, crits, multi-hit, and status effects, advancing the RNG by verified
amounts at each documented step (battle start, before-turn/quick-claw, post-move,
end-of-turn, …). Effect handling lives in `effects.py`; move data comes from
`basedata/moves.json`.

## Observed-path tokens

The observed battle renders as a sequence of tokens (see `path.py`), which the
interactive session compares against each candidate's precomputed path:

| Token | Meaning |
|-------|---------|
| `M###` | Metronome selected move number ### |
| `K<move>` | Magikarp used `<move>` |
| `h` | hit · `!` crit · `-` miss |
| `xN` | multi-hit with N hits |
| `PAR` `FRZ` `SLP` `CFZ` `SCFZ` `FLN` … | status procs / states |

You enter what you observed turn by turn; the tool narrows candidates until one
(or a small set) remains.

## Returns

A list of hex seed strings for the seeds consistent with the observed battle.
