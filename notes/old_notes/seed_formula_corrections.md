# Seed Formula Corrections

Two incorrect assumptions have been discovered. This document describes the bugs, their scope, and what needs to change.

---

## Correction 1: `calculate_seed` uses addition, not OR-with-mask

### The bug

```python
# WRONG (current)
return (mdms << 24) | (time.hour << 16) | (delay & 0xFFFF)

# CORRECT
return ((mdms << 24) | (time.hour << 16)) + delay
```

### Why it matters

The `& 0xFFFF` mask silently discards any delay bits above position 15. Delay 65535 (0xFFFF) is reached in only 65535 / 59.8261 ≈ **18.25 minutes** of DS uptime — not 18 hours. The seedline data confirms delays routinely exceed this: at least four target delays (66290, 67532, 69822, 96668) are above 65535.

For delays below 65536, both formulas produce identical results (no carry, non-overlapping bit ranges). The bug only triggers for higher delays.

When `+ delay` is used and delay ≥ 65536, the excess carries into bits 16–23, which normally hold the RTC hour. This means the hour byte in the computed seed for large delays is **not** simply `time.hour`; it is `time.hour + (delay >> 16)` (ignoring any further carry into mdms). This is apparently correct hardware behavior.

### What breaks

**`calculate_seed`** (times.py:12): the formula itself.

**`generate_times` / `get_times`** (times.py:16–59): currently decodes `delay = key_seed & 0x0000FFFF`. With the addition formula, the lower 16 bits of a high-delay key seed are `delay & 0xFFFF`, not `delay`. The correct extraction is:

```python
base = (key_seed & 0xFF000000) | (key_seed & 0x00FF0000)  # mdms and hour bytes as-is
delay = key_seed - base  # recover full delay by subtraction
```

However, for key seeds (generated at game boot), delays are plausibly below 65536 for typical play sessions — key seed delay is the DS uptime at the moment you load the save, not the battle encounter time. If key seed delays stay below 65536 in practice, `generate_times` continues to work correctly. This should be verified.

**`delay_at_second`** (chart/evaluation.py:44): computes `base_delay + 2 * cumulative_frames(s)`. These computed delays are fed to `calculate_seed` and can easily exceed 65535 after ~18 minutes of a charted window. Any chain file or evaluation result computed while this formula was wrong for delays > 65535 is **invalid and must be regenerated**.

**Cached `.json` time files** (data/times/): If any key seed file was computed with the wrong formula and the key seed had delay > 65535, it is stale. Verify or regenerate.

## Correction 2: Battle encounter seeds have no parity constraint

### The bug

```python
# WRONG (current) — assumes battle delays have same parity as base_delay
start = inputs.target_delay - inputs.window
if (start - base_delay) % 2 != 0:
    start += 1
for d in range(start, inputs.target_delay + inputs.window + 1, 2):
```

The key seed is generated by hardware at a moment that locks its delay to a fixed parity (always odd or always even — the mechanism is at the hardware level). The current code assumes the same parity constraint applies to battle encounter seeds. **It does not.**

Battle encounter seeds can be generated at any delay, regardless of parity. The seed formula step of 2 per game frame still applies within each parity class (frames are 2 delays apart), but both parity classes are now valid entry points. This means the compass was searching only half the candidates.

### What breaks

**`_generate_candidates`** (compass.py:222–253): The parity alignment step (`if (start - base_delay) % 2 != 0: start += 1`) should be removed, and the loop step changed from `2` to `1`. This doubles the candidate count for a given window.

Alternatively, the loop can run separately for each parity, but stepping by 1 is cleaner and equivalent.

**`_seed_reachable`** (compass.py:203–219): Currently implicitly assumes parity via the frame arithmetic. Since both parities are valid, the check needs to consider both cases within the same second.

**Practical impact on the compass**: A window of ±N delays was previously searching ≈ N seed candidates (one per delay, step 2). After the fix it will search ≈ 2N candidates, so the same absolute window now covers twice the range. Existing `window` parameter values in notebooks may need to be halved to maintain roughly the same candidate count, or left as-is for broader coverage.

## Summary of files to change

| File | What changes |
|---|---|
| `claytonlib/times.py` | `calculate_seed`: formula; `generate_times`: delay extraction if key seed delays can exceed 65535 |
| `claytonlib/compass.py` | `_generate_candidates`: remove parity alignment, change loop step to 1; `_seed_reachable`: handle both parities |
| `data/times/*.json` | Potentially stale — verify key seed delays are < 65536, regenerate if not |
| Any `.chain` files with links computed via delays > 65535 | Invalid; must be regenerated |

The chart/evaluation code (`delay_at_second`, `_build_frame_info`) does not call `calculate_seed` directly, but it produces delay values that are fed to `calculate_seed` in compass and chain generation. Those call sites need the corrected formula.
