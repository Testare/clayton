One of the main entrance points for chart.py should be the function chart_safari, which generates the "chart" we'll use to find a target seed. It should have the inputs of key_seed, min_target_seconds, max_target_seconds, strategy, success_criteria, safari_pokemon, and an optional project label to separate projects. We should perhaps create a class to contain these different objects, perhaps call it ChartSafariInput.

We'll then use the key_seed to generate a list of times (all in the year 2000) that generate that seed. We already have a function for this. For each of these times we want to create an evaluation chain, which is basically just a sequence of numbers that comes from evaluating all the links in the chain. We will evaluate all of these chains together, since many will share the same links. We won't generate the chains from the beginning unless min_target_seconds is 0, since it will take time to set up anyways, so for each of these times we'll save a link/second offset of X seconds, and add that to the time before constructing the evaluation chains. Since the chains often share seeds on the same frame, we'll generate all chains simultaneously rather than one at a time, horizontally instead of vertically. I'll refer to the collection of chain links at the same second offset from their initial time as a "frame" or a "row." We should figure out a design so that we don't do duplicate work here: We should only need to evaluate each unique link once per frame, and then apply it to all evaluation chains in that frame that match that link.

Some different ideas for that:
* We can first identify the next link for each chain, and collect them to a set. Then we map each of these links to their number evaluation, and append those number evaluations to each evaluation chain that matches that link, and use some parallel processing here for each unique link. 
* We can create some sort of LazyLinkEvaluation object that is constructed with the chain link tuple. We construct one of the objects for each unique link, keep our own "master" set of all of them, and also each chain maintains a list of these objects. Since lists containing the same object are not passed-by-copy, when we reach a point where we want to write the results to a file, we iterate through all and force them to actually evaluate once and store the resulting value.
* We can also just use @lru_cache on the evaluation function and iterate through the chains one at a time, having python's memoization take care of it, and then clear the cache after each frame. 
* There might be some library feature that makes this easier.

This is a part that needs some design consideration, and we might implement multiple approaches and use benchmarks/timing functions to figure out which is the most performant, so it would be good if it was easy to swap these implementations. That might mean polymorphism or use of generics in the case of the LazyLinkEvaluation objects. In any case, we'll run these frames until we reach the max_target_seconds, at which point each chain should have (max_target_seconds-min_target_seconds+1) evaluation links/numbers, and each file should have that many bytes times eight.

In any case, we'll want some construct for each evaluation chain to assist in writing these evaluation numbers to chain files. Since we'll have potentially thousands of chains, we might not want to write to each one after each frame, we'll probably want to accumulate in memory for a certain amount of frames, and then write to each file sequentially once we reach that amount. This number should be configurable, maybe just through a module variable with public getter/setter methods. Once we write the values to the files, we should drop them from memory. I'll refer to the process of evaluating X frames and then writing them all to files as a write cycle, and we can refer to X as "evaluation_frames_per_write_cycle"

Each chart should save its output in the `./data/<projectLabelIfItExist/><pokemon>_<8 digit hex key_seed>/chart_<strategy>_<criteria>/` directory. Chains should be saved with file names `<ISO date tim>+<min_target_seconds>.chain`. I've considered keeping all chains in a single file, but I think that'll make it more annoying when we actually want to use the charts to find a good target.

This process needs to be interruptable and resumable. Starting again with the same parameters should implicitly resume. When resuming work that has already been in progress, we will first "square off" the chains. We find the size of each file, then take smallest file's size, rounded down to the nearest multiple of 8, and then truncate all files to be that size if they aren't already. We then divide this bytesize by 8, and that's the number of seconds/links in each chain, so we can jump ahead that many seconds/frames and resume from there.

We should be sure to add logging, especially to indicate performance. For each write cycle, we should log how long the evaluation process took (If we do lazy evaluation, we should log both the chain construction part and the actual evaluation steps), and how long the writing to file took. We can use this to optimize later.
